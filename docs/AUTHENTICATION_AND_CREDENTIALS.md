# Authentication & Credential Architecture

## Overview
The Financial Ledger Engine supports dual-channel, session-based authentication:
1. **Google OAuth2 / OIDC** (federated identity via Google accounts)
2. **Email & Password Authentication** (native identity via salted BCrypt password credentials)

Both authentication paths integrate with Spring Security's native `SecurityContext` and issue standard, HTTP-only session cookies (`JSESSIONID`). The system avoids JWTs, refresh tokens, and client-side credential storage.

---

## Session Model
- **Storage**: Server-side `HttpSession` managed by Spring Security (`HttpSessionSecurityContextRepository`).
- **Client Transport**: HTTP-only, SameSite-compliant session cookies (`JSESSIONID`).
- **Session Fixation**: Protected via `changeSessionId()` on authentication.
- **Identity Resolution**: `AuthenticatedUserService` abstracts principal resolution across `CustomOAuth2User`, `CustomOidcUser`, standard `UserDetails`, and `Authentication.getName()`.
- **Session Lifetime**: Bound by application session timeout; invalidated explicitly upon `POST /logout`.

---

## Credential Storage & Database Schema
Password credentials are stored in an isolated, dedicated database table (`user_credentials`) rather than polluting the core `users` entity. This ensures user queries never inadvertently leak password hashes.

### Schema (`V7__create_user_credentials.sql`)
```sql
CREATE TABLE user_credentials (
    id UUID PRIMARY KEY,
    user_id UUID NOT NULL,
    password_hash VARCHAR(255) NOT NULL,
    created_at TIMESTAMP WITH TIME ZONE NOT NULL,
    updated_at TIMESTAMP WITH TIME ZONE NOT NULL,
    CONSTRAINT uk_user_credentials_user_id UNIQUE (user_id),
    CONSTRAINT fk_user_credentials_user_id FOREIGN KEY (user_id) REFERENCES users(id) ON DELETE CASCADE
);

CREATE INDEX idx_user_credentials_user_id ON user_credentials(user_id);
```

### Invariants:
- Exactly one credential record per user (`uk_user_credentials_user_id`).
- Deleting a user cascades and purges their credentials (`ON DELETE CASCADE`).
- Password hashes only. Plaintext passwords are never persisted, logged, or returned in API responses.

---

## Password Hashing & Policy
- **Algorithm**: `BCryptPasswordEncoder` with strength/work factor 12.
- **Salting**: Automatic per-hash cryptographically secure random salt generated by BCrypt.
- **Password Strength Policy**:
  - Length: Between 8 and 128 characters.
  - Composition: Must contain at least one letter (`[a-zA-Z]`) and at least one digit (`[0-9]`).
  - Validation: Enforced on both frontend forms and backend services (`PasswordPolicyValidator`).

## Endpoints

### 1. User Signup
- **Endpoint**: `POST /api/v1/auth/signup`
- **Request Body**:
  ```json
  {
    "name": "Alice Smith",
    "email": "alice@example.com",
    "password": "SecurePassword123"
  }
  ```
- **Response**: `201 Created`
  ```json
  {
    "id": "44c1d719-6d0c-489f-97bb-ab063c7c597d",
    "email": "alice@example.com",
    "name": "Alice Smith"
  }
  ```
- **Behavior**:
  - Validates name, normalized email (lowercased, trimmed), and password policy.
  - Rejects duplicate email with `409 Conflict`.
  - Atomically creates `User` and `UserCredential` in a single transaction.
  - Automatically establishes an authenticated session in `SecurityContext`.

### 2. User Login
- **Endpoint**: `POST /api/v1/auth/login`
- **Request Body**:
  ```json
  {
    "email": "alice@example.com",
    "password": "SecurePassword123"
  }
  ```
- **Response**: `200 OK`
  ```json
  {
    "id": "44c1d719-6d0c-489f-97bb-ab063c7c597d",
    "email": "alice@example.com",
    "name": "Alice Smith"
  }
  ```
- **Error**: `401 Unauthorized` with generic message `"Invalid email or password"` for non-existent users, missing credentials, or invalid passwords.

### 3. Password Linking
- **Endpoint**: `POST /api/v1/auth/link-password`
- **Authorization**: Requires authenticated user session.
- **Request Body**:
  ```json
  {
    "password": "NewSecurePassword123"
  }
  ```
- **Response**: `200 OK`
- **Behavior**: Links or updates the password hash for the authenticated user (e.g., users originally registered via Google OAuth).

### 4. Authenticated User Profile
- **Endpoint**: `GET /api/v1/auth/me`
- **Authorization**: Requires authenticated session.
- **Response**: `200 OK` with `UserResponseDto` (id, email, name).

### 5. Session Logout
- **Endpoint**: `POST /logout`
- **Response**: `200 OK`
- **Behavior**: Invalidates the HTTP session, clears authentication context, and clears `JSESSIONID` cookie.

## Google OAuth & Password Account-Linking Rules

### Case A: User signs up with email/password and later uses Google with the same email
- **Behavior**: Google OAuth synchronizes identity by verified email (`UserService.syncOAuth2User`).
- **Result**: Resolves and maps to the existing application `User` entity.
- **Safety**: The existing password hash in `user_credentials` remains intact. The user can authenticate using either Google OAuth or email/password.

### Case B: User first signs in with Google and later wants email/password access
- **Behavior**: User logs in with Google and navigates to settings/profile to link a password via `POST /api/v1/auth/link-password`.
- **Result**: Validates and hashes the password, saving a new record into `user_credentials`.
- **Safety**: Requires an already authenticated session, preventing unauthorized credential injection.

### Case C: User attempts to register with an email already associated with Google
- **Behavior**: `POST /api/v1/auth/signup` checks `userRepository.existsByEmail(normalizedEmail)`.
- **Result**: Registration is rejected with `409 Conflict` (`"An account with this email already exists"`).
- **Safety**: Prevents account takeover attacks where an unauthenticated actor attempts to claim a Google user's account by registering their email with a password.

## Security Decisions
1. **Protection Against Account Enumeration**:
   Login failures uniformly return `401 Unauthorized` with the generic error `"Invalid email or password"` regardless of whether the email exists, has no credentials, or provided an incorrect password.
2. **Session Fixation Mitigation**:
   Configured `sessionFixation().changeSessionId()` on authentication to prevent session hijacking via pre-set session identifiers.
3. **CORS & Cookie Isolation**:
   `Access-Control-Allow-Credentials: true` with strict allowed origin whitelist (`http://localhost:3000`, `http://localhost:3001`). Credentials and session cookies are never exposed to arbitrary origins.
4. **Defense in Depth**:
   `user_credentials` is a separate table, preventing `User` queries across the application from exposing password hashes in memory or serialized responses.
