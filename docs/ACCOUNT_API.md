# Account Management API Specification (V5)

The Account Management API provides endpoints for authenticated users to create and manage their retail checking accounts (`USER_CHECKING`), inspect account metadata, and view balances.

---

## 1. Architectural Principles & Security Rules

1. **Authentication Required**: All endpoints require an authenticated user principal (via Google OAuth2 / session identity). Unauthenticated requests return `HTTP 401 Unauthorized`.
2. **Server-Side Ownership Enforcement**: The user identity is resolved strictly from the authenticated security principal (`AuthenticatedUserService`). Clients cannot specify `userId`, `user_id`, or claim ownership of other accounts.
3. **Strict Account Type Isolation**:
   - Only `USER_CHECKING` accounts can be created or queried by users.
   - Platform clearing accounts (`SYSTEM_CLEARING`) are internal system accounts (`user_id = NULL`) and are never creatable or viewable through these endpoints.
4. **Anti-Enumeration Protection**:
   - Requests for an account belonging to another user, a nonexistent account, or a system account all return `HTTP 404 Not Found`. This prevents external probing and enumeration of existing account IDs.
5. **No Mutation of Financial Status or Balances**:
   - Balance is initialized strictly to `0.0000`. Clients cannot specify an initial balance.
   - Status starts strictly as `ACTIVE`. Clients cannot set status or mutate status via these endpoints.
   - Account numbers are deterministically formatted and generated by the server (`ACCT-` followed by 12 uppercase hexadecimal characters).

---

## 2. Endpoints Overview

| Method | Endpoint | Description | Success Status | Auth Required |
|---|---|---|---|---|
| `POST` | `/api/v1/accounts` | Create a new checking account | `201 Created` | Yes |
| `GET` | `/api/v1/accounts` | List all checking accounts owned by caller | `200 OK` | Yes |
| `GET` | `/api/v1/accounts/{accountId}` | Get account details by ID | `200 OK` | Yes |

---

## 3. Endpoint Specifications

### 3.1. Create Account

#### `POST /api/v1/accounts`

Creates a new `USER_CHECKING` account for the authenticated user in the requested currency.

##### Request Headers
| Header | Value | Required |
|---|---|---|
| `Content-Type` | `application/json` | Yes |

##### Request Body
```json
{
  "currency": "USD"
}
```

##### Field Constraints
| Field | Type | Required | Constraints | Description |
|---|---|---|---|---|
| `currency` | `string` | **Yes** | Exactly 3 uppercase alphabetic characters (`^[A-Z]{3}$`) matching ISO 4217 | Account currency |

> **NOTE on Currency Validation**:
> Lowercase or non-standard currency inputs (such as `"usd"`, `"US"`, or `"USDT"`) are rejected with `HTTP 400 Bad Request` to strictly align with the PostgreSQL check constraint `chk_accounts_currency_format`. Silently normalizing currencies is intentionally disallowed.

##### Success Response (`201 Created`)
```json
{
  "accountId": "b47514a6-7786-4f40-9759-99419cf629ec",
  "accountNumber": "ACCT-4A9B3E2F1C0D",
  "accountType": "USER_CHECKING",
  "status": "ACTIVE",
  "currency": "USD",
  "balance": 0.0000,
  "createdAt": "2026-09-23T15:20:00.123456Z",
  "updatedAt": "2026-09-23T15:20:00.123456Z"
}
```

##### Error Responses
- `400 Bad Request`: Missing currency, blank currency, or invalid currency format.
- `401 Unauthorized`: Unauthenticated request.

### 3.2. List Accounts

#### `GET /api/v1/accounts`

Returns a chronological list of all `USER_CHECKING` accounts owned by the authenticated caller.

##### Success Response (`200 OK`)
```json
[
  {
    "accountId": "b47514a6-7786-4f40-9759-99419cf629ec",
    "accountNumber": "ACCT-4A9B3E2F1C0D",
    "accountType": "USER_CHECKING",
    "status": "ACTIVE",
    "currency": "USD",
    "balance": 1500.0000,
    "createdAt": "2026-09-23T15:20:00.123456Z",
    "updatedAt": "2026-09-23T15:25:30.987654Z"
  },
  {
    "accountId": "7a3512b9-1f48-4cb2-8e10-48e02d9921c3",
    "accountNumber": "ACCT-8C1D9F4E2A3B",
    "accountType": "USER_CHECKING",
    "status": "ACTIVE",
    "currency": "EUR",
    "balance": 0.0000,
    "createdAt": "2026-09-23T15:30:00.654321Z",
    "updatedAt": "2026-09-23T15:30:00.654321Z"
  }
]
```

If the user owns no accounts, returns an empty array `[]` with status `200 OK`.

### 3.3. Get Account by ID

#### `GET /api/v1/accounts/{accountId}`

Retrieves account metadata and snapshot balance for a specific account owned by the authenticated caller.

##### Path Parameters
| Parameter | Type | Required | Description |
|---|---|---|---|
| `accountId` | `UUID` | **Yes** | Unique identifier of the account |

##### Success Response (`200 OK`)
```json
{
  "accountId": "b47514a6-7786-4f40-9759-99419cf629ec",
  "accountNumber": "ACCT-4A9B3E2F1C0D",
  "accountType": "USER_CHECKING",
  "status": "ACTIVE",
  "currency": "USD",
  "balance": 1500.0000,
  "createdAt": "2026-09-23T15:20:00.123456Z",
  "updatedAt": "2026-09-23T15:25:30.987654Z"
}
```

##### Error Responses
- `400 Bad Request`: Malformed UUID string in path.
- `401 Unauthorized`: Unauthenticated request.
- `404 Not Found`: Account does not exist, belongs to another user, or is a system account.

---

## 4. Balance & Status Semantics

- **Snapshot Balance**: The `balance` returned in the response represents the current row snapshot in PostgreSQL. It is updated atomically by double-entry transfers (`TransferService`).
- **Audit Verification**: Analytical verification comparing the snapshot balance against immutable ledger entries is performed via the dedicated Reconciliation API (`/api/v1/reconciliation/accounts/{accountId}`).
- **Status Lifecycle**: Accounts are created with `ACTIVE` status. Transitions to `FROZEN` or `CLOSED` are administrative compliance operations and are not exposed to retail user self-service.
